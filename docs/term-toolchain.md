# term 作者工具链：设计

> 口径来源：`docs/kernel.md`（内核设计，唯一权威）、`docs/plugins.md`（插件契约）、`docs/host.md`（载体设计）。
> 本文件属 `docs/`，只写设计，不含实施步骤；冲突时以 `kernel.md` 为准。

---

## 一、问题

归约机与原语已在内核就位，但生产世界里没有任何判定以 term 形态存在——判定全部写在插件的 `execute/` 服务代码里。原因有二：

1. **表达力缺口**：`cmp` 产出 `Int`（-1/0/1），`if` 要求条件为 `Bool`，而没有任何原语把比较结果变成 `Bool`。`if a < b then X else Y` 写不出来，判定无法表达为 term；且 `g` 只读 `ctx`，判定无法读取运行时值的字段。
2. **作者面缺口**：即便补上判定核，判定仍要手写原语的 JSON AST——无类型、无 IDE、无调试、无测试工具。第一方尚难维护，第三方作者会被挡在门外。

本设计只解决第二个缺口（作者面）并给出第一个缺口（判定核）的设计口径；两者共同构成「判定作为数据」这条路线的前置。

---

## 二、分层与边界

三层，职责不可混：

```
源（作者写）  →  编译（写期，作者侧）  →  term AST（数据，入世界）
```

- **源**：作者表达判定的表面形式。两种形态共用同一语义，编译到同一 AST（见 §三）。
- **编译**：写期发生，纯函数、确定性。产物是数据（原语 AST），与手写 term 同路重放。
- **term AST**：入世界的 `Def.body`。运行期只有它，编译器不在运行路径上。

**边界（硬）**：

- 编译器**不进宿主、不进内核**。宿主「不认识语义」（`host.md` §五 路由），把源 DSL 编译成原语属语义理解，只能住作者侧。
- 编译器**不是插件运行时依赖**。插件包不得 import 内核/宿主（`plugins.md` 红线 1）；编译器是作者侧的构建工具，与运行期产物分离。
- 运行期判定**只是数据**：改判定 = 数据世代（`add_gen` / 换 def），进程不动（`plugins.md` §五 换代表）。

## 三、源面

两种形态，语义等价，编译到同一 AST。二者可并存：糖化 JSON 是规范中间格式，宿主语言 builder 是作者体验层。

### 3.1 糖化 JSON（规范中间格式）

糖化 JSON 是带 `k` 判别位的表达式对象，比原语高一层，编译期机械降级（完整规范见 `toolchain/spec.md`）：

```
{ k:'lit', v }                   → ["c", v]
{ k:'ctx', path }                → ["g", path]
{ k:'get', of, path }            → ["get", of, path]
{ k:'arg', i }                   → ["v", i]
{ k:'if', cond, then, else }     → ["if", cond, then, else]
{ k:'pred', op, a, b }           → ["pred", op, a, b]（见 §五）
{ k:'fold', coll, init, step }   → ["fold", coll, init, ["c", { $ref: step }]]
{ k:'call', ref, args }          → ["call", ["c", { $ref: ref }], args]
{ k:'eff', port, method, args }  → ["eff", port, method, args]
{ k:'let', ... }                 → 写期宏展开（替换，不产生原语）
```

- `fold.step` / `call.ref` 的函数侧写**包内相对路径**（`terms/foo.json`），降级时包成 `["c", { $ref: path }]`；入世时由宿主按 `plugins.md` A0b 的 `$ref` 机制机械替换成 callee def 哈希，得 `["c", <hash>]`。糖化层的 `ref` 与 A0b 的 `$ref` 是同一机制。
- 糖化 JSON 是**跨语言的稳定交换格式**：任何语言的 builder 都产出它，任何语言的读者都能读它。它不含实现细节，只含判定语义。

### 3.2 宿主语言 builder（类型化写期宏）

作者用宿主语言（TS / Rust / Python…）写一个**构建脚本**，调用类型化 builder 生成糖化 JSON 或直接生成 AST：

```
const body = t.if(t.pred('lt', t.arg(0), t.lit(10)), t.eff('fs', 'read', t.ctx(['ids','x'])), t.lit(null))
```

- 运行在**构建期**，不是运行期。产物是数据；判定仍是数据。
- 得到宿主语言的全部工具：类型、IDE、单测、重构。
- builder 只能在原语可表达的范围内构造；超出即编译期报错。
- 这是「`let` 可派生 ⇒ 永远是写期宏」的落地：宏展开在构建期完成，展开产物是数据（`kernel.md` §十三）。

**构建期计算是允许的**（生成常量、批量展开），但**运行期判定不得依赖构建期状态**：builder 的输入只有源；同源必得同 AST（见 §六 确定性）。校验器负责拦住把运行期语义藏进构建期的写法（如按构建时间戳生成不同 term）。

## 四、降级（lowering）

糖化层到原语的机械映射，逐条：

| 糖化 | 原语 | 说明 |
| --- | --- | --- |
| `lit` | `["c", v]` | 字面量 |
| `ctx` | `["g", path]` | 静态字面路径；缺失抛 `missing_path` |
| `get` | `["get", of, path]` | 对任意值沿静态 path 投影；缺失抛 `missing_path` |
| `arg` | `["v", i]` | 位置参数 |
| `let` | — | 写期宏：以替换展开，不产生原语；重复出现按哈希共享（同名 `let` 只展开一次） |
| `if` | `["if", cond, a, b]` | 惰性，只求一支；`cond` 必须产 `Bool` |
| `pred` | 判定核谓词 | 见 §五；产 `Bool` |
| `call` | `["call", hash, [args]]` | 函数即值；callee 是本身份内 term def |
| `eff` | `["eff", port, method, args]` | 产 `EffRequest`；每 directive 至多一个挂起点 |
| `fold` | `["fold", coll, init, step]` | step 是本身份内 term def，签名 `[acc, item, index]` |

**表达力边界（两类，性质不同）**：

- **lambda / 递归 / while：内核设计明确拒绝，不是工具链的选择。** 三条理由在 `kernel.md` §十三 写死：① 递归要求自引用，而 def 键 = `H(Def)`，自引用即哈希循环，**内容寻址下不可能**；② 运行期构造的函数无哈希、无世代、无 `pins`/`sig`，进不了依附与判决（「不可派生且证明后仍拒绝」，是内核负资产）；③ `while` 的任意迭代破坏结构性终止——调用图恒为 defs DAG 的子图，迭代由 `fold` 按集合长度界定，`gas` 只是资源上界。加这三样**不是加原语，是换模型**；生成性需求由「写期生成 + 多次续跑」承担。
- **算术 / 数据构造：已提供，边界是「有限数」与「新值来源」。** 原语已有 `arith`（`add` / `sub` / `mul`，**无 `div`**）、`list`（构造新列表）、`obj`（构造新对象）、`getOr`（安全投影）；工具链据此提供对应糖化键。数值计算与结构构造因此可写成 term，不再一律归执行件（经 `eff`）。仍不提供 lambda / 递归 / while（内核设计拒绝，见上条）。
- 由此定位：**term 表达「选择与编排」**（按运行时数据分支、从候选中选、遍历列表取匹配/极值、决定发哪个效果）。这是当前边界下「term 该写什么」的判据，不是永久边界。

## 五、内核依赖：判定核补全（谓词桥 + 值投影）

工具链依赖内核补两处：`if`/`pred` 依赖「比较 → 布尔」这座桥，`get` 依赖「值投影」。两处都是**内核公共面变更**，均已落地；本节记录既成事实。

判定核按**方案甲**落地：新增布尔谓词原语 `["pred", op, a, b]`（op ∈ `lt`/`le`/`gt`/`ge`/`eq`/`ne`），返回 `Bool`，复用 `cmp` 的全序口径；显式、无隐式转换，符合 `value.ts`「不做隐式转换」的口径。未采用「放宽 `if` 接受 `Int`」的方案乙。工具链的 `pred` 糖化即降级到该原语；`if` 的 `cond` 必须产 `Bool` 的口径不变。

`pred` 与 `get` 连同既有 `arith` / `list` / `obj` 等在内，内核原语**共 14 个**（`machine.ts` 的 `TERM_TAGS`）：`c` / `g` / `get` / `getOr` / `v` / `cmp` / `pred` / `if` / `fold` / `eff` / `call` / `arith` / `list` / `obj`。

都是**加语义**（老日志里这些输入本就报错），向后兼容：老实现遇新原语报 `bad_term`、遇新条件类型报 `bad_cond`，拒绝执行而非算错——满足「原语只增不改语义」（`kernel.md` §十三）。

### 5.2 值投影 `get`

`g` 的根固定是 `ctx`（静态），判定读不到运行时值的字段（如 `item.score`），任何结构化数据上的选择都写不出。故补 `["get", value, path]`：对任意值沿静态 path 投影，复用与 `g` 同一的 `walk` 口径，与 `g` 对称（`g` 的根是 `ctx`，`get` 的根是任意值）。缺失 / 穿标量抛 `missing_path`；空 path 返回该值本身。同为加法式扩展，向后兼容。工具链的 `get` 糖化据此降级。

## 六、静态校验、错误定位与确定性

### 6.1 静态校验

编译期机械检查，不过即拒编译（fail-closed）：

- 形态：未知糖化键、缺必填键、类型不符。
- 路径：`ctx` / `get` 路径为 `(str|int)` 数组（空数组合法：`g` 得整个 `ctx`，`get` 得该值本身）。
- 引用：`call`/`fold` 的 `ref` 指向包内存在的 term；无环（与 A0b 的 `term_cycle` 同口径，工具链提前检出）。
- 效果：`eff` 的 `port` 必须是插件自身 `implements` 或 `pins` 里的能力类。**方法名校验两侧刻意不同**：自调用（`port ∈ implements`，或仅声明了 `methods` 的能力类）的 `method` 必须在该能力类的 `methods` 声明内，工具链可机械校验；跨身份（`port` 只在 `pins` 里）的方法名住在**被调身份**的声明里，工具链只有单包源、看不到被调声明，故**放弃方法名校验**。宿主入世期看得到被调身份的世界声明，按被调方 `methods` 补上这一步（自调用入世期同样机械校验）；被调身份未入世时按既有 `pins` 解析失败路径处理，不新增拒绝语义。两侧可见信息不同，口径因此不同，不是缺陷。跨身份调用只能经 `eff`，本身份内才可 `call`（`plugins.md` §三 红线 4）。
- 边界：不得出现算术/构造/递归形态（本就不提供语法，校验兜底）。
- 确定性：编译不读时间/随机/环境；同源必得同 AST。

### 6.2 错误定位

- **静态错误**（校验器）带**源 JSON 指针**，直接定位到糖化节点。
- **运行期错误**：机器在错误里带失败节点路径 `at`（当前 def 内）、`def`（失败发生在被调 term 内时的被调 def 哈希）、`callAt`（调用点路径）。`testkit.runTerm` 原样透出；`explainError(program, termPath, error)` 据此映射回**糖化源指针**（`{ term, pointer, approx }`）。
- `approx: true` 表示因 `let`/`bind` 写期展开等原因，指针只到最近的可见节点。工具链不在 term 里插桩（不改判定数据与哈希）。

### 6.3 确定性

同源 → 同糖化 JSON → 同 AST → 同 def 键。这是「改判定 = 数据世代」的前提：判定源没变，重编译必得同一哈希，不产生无意义换代。builder 与编译器都不得引入非确定性输入。

## 七、测试面

测试器与编译器**分属两个入口**，因为二者对内核的依赖不同：

- **编译器（`toolchain` 主入口）零内核依赖**：只解析 / 校验 / 降级 / 出源映射，不 import 内核。入世时 callee 哈希由宿主按 A0b 替换，编译器不需要 `H`/`canonicalJson`/求值机。这是「插件构建脚本可 import 它」的前提（见 §八）。
- **测试器（`toolchain` 的独立入口）**：给定 `ctx` / `args` / `effects` 回灌表，调用内核 `evaluate` 求值，断言结果与错误码；与内核共用同一求值实现，不另写一份口径。它**由外部工具调用，不放进插件包**——插件只交 fixture，内核依赖因此不进入插件。

- 判定单测：对同一判定，覆盖各分支（含边界值、缺失路径、挂起效果、`eff_error`）。
- 确定性测试：同源两次编译逐字节一致；同输入两次求值逐字节一致。
- 回归测试：判定源变更后，旧世代仍可重放（旧 term 在链上，数据不动）。

## 八、位置、依赖边界与分发

- **位置**：独立顶层包 `toolchain/`（**非 `packages/`**——`packages/` 是运行时载体实现，工具链是作者侧构建期工具，两者不同层）。
- **依赖边界（写死，三条单向）**：
  1. `packages/{kernel,host,boot,client}` 任何包**不得依赖** `toolchain`（运行时不得依赖工具链；否则宿主 import 它去校验 term 即「宿主认识语义」）。
  2. 插件**仅不入世的构建/开发脚本**可 import `toolchain` 的编译器（`.worldignore` 排除该脚本）；插件运行期（`execute/` / `src/` / `terms/` / `schema/` / `plugin.json`）与入世内容**不得** import。编译器零内核依赖，故该 import 不传递内核。
  3. `toolchain` **至多依赖内核**（仅测试器入口，见 §七），不进运行路径。
- **`toolchain` 不是插件、不是身份**：不进 ①、不进 `state/plugins.json`、不参与 `pins`/路由/装配/生命周期。其产物作为**属主插件的数据**入世。
- **源的位置**：判定源住插件包内（如 `terms/` 下的糖化 JSON 或构建脚本）。源与产物同包、随包入世与否由 `members` 声明决定。
- **产物**：编译产出的原语 term（`terms/*.json`）是运行期产物，入 ①。源映射与构建脚本是作者侧派生物，可不入世（`.worldignore` 声明）。
- **构建步骤**：编译作为插件 `plugin.json.build` 的一步（宿主只执行、不解释，与现有构建声明同性质）。宿主不认识源 DSL，只跑声明的命令。
- **入世校验**：宿主 `validate_package` 的 dry-run 仍只做机械校验（形态 / `$ref` 环 / 路径安全），不解释糖化语义；语义校验在工具链侧完成。
- **跨语言**：糖化 JSON 是交换格式，多语言 builder 产出同一格式、同一 AST，判定语义不随语言分叉。
- **版本**：糖化格式与编译器各自带版本；编译产物不带版本（内核已按「未知原语报 `bad_term`」处理跨版本）。

## 九、明确不做

- 不把 lambda / 递归 / while 纳入（内核设计拒绝，理由见 §四；加它们属换模型，不属原语扩展）。
- 算术 / 数据构造语法**已提供**（`arith`（`add`/`sub`/`mul`，无 `div`）/ `list` / `obj` / `getOr`，见 §四），不属「不做」。
- 不把编译器放进宿主或内核；`toolchain` 不进 `packages/`。
- 不把源映射、构建脚本塞进 ①。
- 不做可视化判定编辑器（后置，若需要再单独立项）。
- 不改原语既有语义（判定核补全只加不改，见 §五）。
- 不承诺「判定可表达一切逻辑」——term 的定位是选择与编排，不是通用计算。
