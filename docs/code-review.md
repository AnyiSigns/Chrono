# 代码审查规范（Agent + 子代理版）

> 适用范围：本规范定义由 **Agent（主代理）** 在收到代码变更后，调用若干 **子代理（Subagent）** 完成从**预检**到**裁决合并**的代码审查方式。
> 这里没有独立的工作流引擎，也没有专门的"编排 Agent"：主 Agent 本身就是协调者，按需把任务分派给子代理，汇总结论后裁决。
> 人类仅作为**代码作者**与**规范制定者**：编写代码、维护《编码规范》；审查、评论、裁决、合并由 Agent 及其子代理完成。
> 目标：以可复现、可配置、零人为瓶颈的方式保障代码质量，让审查速度不受人力限制。

---

## 1. 目标与原则

1. **审查零人为瓶颈**：评审、评论、裁决、合并均由主 Agent 调度子代理按既定规则自动完成，不依赖人工排队。
2. **规范即唯一标准**：所有判定标准直接来自《编码规范》，不存在脱离规范的独立规则集；规范改一处，审查行为即随之改变。
3. **可复现、可解释**：每次审查输出结构化报告，每条结论都能追溯到具体规范条款与代码位置。
4. **分级自治**：主 Agent 按问题级别自动决定是"阻塞合并"还是"记录跟进"，无需人工拍板。
5. **持续自进化**：审查结果回流《编码规范》，形成闭环优化。

---

## 2. 角色与职责

| 角色 | 性质 | 主要职责 | 关键产出 |
|------|------|----------|----------|
| **作者（Author）** | 人类 | 编写代码、编写变更说明、按 Agent 反馈修订 | 合规代码、清晰描述 |
| **主 Agent（Agent）** | Agent | 接收变更、按需调用子代理、汇总结论、裁决与合并 | 结构化审查报告、合并/驳回决策 |
| **测试生成子代理（Test Author）** | 子代理 | 为作者新增/改动代码编写并补全测试，提升覆盖率 | 可运行的测试代码、覆盖率报告 |
| **预检子代理（Precheck）** | 子代理 | 格式化、Lint、类型检查、运行测试、覆盖率、依赖漏洞 | 可复现的预检报告 |
| **评审子代理（Reviewer）** | 子代理 | 按《编码规范》评估设计/可读性/正确性/安全，产出分级评论 | 结构化评审报告 |
| **安全/依赖子代理（Security）** | 子代理 | 漏洞扫描、license 风险、secret 扫描 | 安全合规报告 |
| **端到端测试子代理（E2E）** | 子代理 | 运行/生成端到端测试，验证跨模块、跨服务关键路径 | E2E 测试报告、失败轨迹 |
| **裁决（Gatekeeper）** | 主 Agent 职责 | 依据级别与门禁规则裁决是否合并，执行合并或打回 | 合并/驳回决策与提交历史 |
| **规范维护者（Maintainer）** | 人类 | 维护《编码规范》、处理误报、回流审查经验 | 规范更新 |

> 说明：本规范不使用独立的工作流/编排层。主 Agent 直接承担"触发、调度、汇总、裁决"职责，子代理是它在审查过程中按需创建的专项执行单元（如预检、评审、安全、E2E），彼此通过结构化消息（JSON）通信，而非经由某个状态机流水线。

### 2.1 作者职责

- **作者只负责编写业务代码与变更说明，不负责编写测试**；测试由测试生成子代理按变更面自动补全（见第 2.3 节与第 3 节）。
- 提交前完成自检（见第 4 节），尽量让预检一次通过。
- 提供结构化变更说明（见第 5 节），供主 Agent 与子代理理解意图与影响面。
- 收到 Agent 的阻塞评论后，按建议修订并重新提交；对误报可在变更说明中以 `@agent-ignore: <规范条款> <理由>` 显式豁免（仅限规范维护者认可的场景）。
- 不绕过门禁（如强制跳过检查）提交到受保护分支。

### 2.2 主 Agent 通用职责

- 收到变更后，自行决定调用哪些子代理、按何种顺序、是否需要并行；不存在预设的固定流水线阶段。
- 所有行为必须**幂等、可重放**：相同输入产生相同结论。
- 每条结论携带：规范条款、严重级别、文件:行、问题描述、建议、置信度。
- 不输出模糊主观评价（如"这段代码不好"），只输出可判定、可引用的结论。
- 跨子代理通过结构化消息（JSON）通信，避免自然语言歧义。

### 2.3 子代理职责

- 子代理由主 Agent 在一次审查会话中创建，目标单一、边界清晰（如"只做预检""只做评审"）。
- 每个子代理只产出其职责范围内的结构化结论，不跨职责重复判定。
- **测试生成子代理**在读到作者变更后，基于新增/改动的函数与分支自动编写测试：
  - 覆盖正常路径、边界值与异常分支；优先复用现有测试框架与脚手架，与项目测试风格一致。
  - 对难以单测的外部依赖（网络、DB、时钟等）使用桩/模拟，保持测试可隔离、可重复运行。
  - 输出新增测试清单、断言点、覆盖率增量；对无法稳定覆盖的部分标注 `confidence` 与理由，交评审子代理或规范维护者确认。
  - 测试代码同样受《编码规范》约束，由预检/评审子代理一并检查，不因为是 Agent 生成而降低标准。
- 预检子代理已覆盖的格式/Lint/类型/覆盖率问题，评审与安全子代理不再重复输出，除非存在交叉判定（如命名影响可读性）。
- E2E 子代理在单元/集成测试通过后运行，验证**真实链路**：跨模块、跨服务、跨进程的关键用户路径（如"登录→下单→支付"）：
  - 优先运行与本次变更相关的用例（基于影响面分析），全量 E2E 作为门禁兜底，控制时长。
  - 失败时输出：失败用例、入口请求、各阶段状态、日志/追踪片段，定位到具体服务与步骤。
  - 具备测试生成能力：对新增关键路径，若缺 E2E 覆盖则自动生成骨架用例，标注 `confidence` 供人工/规范维护者确认。
  - 环境隔离：使用独立的可销毁 E2E 环境（容器/临时命名空间），不影响生产与其他流水线。

## 3. 审查执行（主 Agent 调用子代理）

没有固定工作流，主 Agent 按变更特征灵活调度子代理。典型执行模式如下（仅供参考，主 Agent 可调整）：

```
作者提交 ──► 主 Agent 接收变更与变更说明
                  │
                  ▼
        分析变更影响面，决定调用哪些子代理
                  │
        ┌─────────┼──────────┬──────────────┬──────────────┐
        ▼         ▼          ▼              ▼              ▼
  测试生成子代理 预检子代理 评审子代理  安全/依赖子代理  端到端测试子代理
  (先补全测试)  (跑测试/    (设计/可读/   (漏洞/license/   (关键用户路径/
              覆盖率)     正确性)        secret 扫描)      跨服务集成验证)
        │         │          │              │              │
        └─────────┼──────────┴──────────────┴──────────────┘
                  ▼
        主 Agent 汇总各子代理报告
                  │
   存在🔴/确认的🟠？ 或 E2E 失败？
          /              \
        是                否
        │                 │
        ▼                 ▼
   打回作者(带评论)   主 Agent 裁决门禁
        │                 │ 全部门禁满足？
        │            ┌────┴────┐
        │           是         否
        │            │          │
        │            ▼          ▼
        │        自动合并    继续等待/打回
        │            │
        └──── 作者修订后重新进入审查
```

- **测试生成子代理通常最先运行**：作者不写测试，主 Agent 先让其补全测试，再由预检子代理运行这些测试并度量覆盖率，后续评审/安全/E2E 在此基础上进行。
- 主 Agent 可根据变更规模裁剪子代理：纯格式改动可只跑预检子代理；新增对外能力必须跑安全与 E2E 子代理。
- 子代理之间不直接互相调用；所有结论统一回到主 Agent，由主 Agent 去重、分级、裁决。

---

## 4. 提交前自检（作者 + 本地检查）

> 作者不编写测试；测试由测试生成子代理补全。作者侧的"测试"自检改为确保代码**可测**：结构清晰、依赖可注入、行为确定，便于子代理生成稳定测试。

- [ ] 变更已按单一职责拆分，单 PR ≤ 400 行有效变更
- [ ] 通过本地格式化
- [ ] Lint / 类型检查无新增告警
- [ ] 代码可测：函数/模块职责单一、外部依赖可桩、无隐藏全局状态
- [ ] 无密钥、调试代码、计划编号、注释掉的死代码
- [ ] 自查与《编码规范》《计划文件》一致

> 作者侧的本地检查可由轻量 Agent提前拦截明显问题。

## 5. 评论分级标准（Agent 产出）

Agent 评论必须带级别与规范条款，便于自动裁决：

| 级别 | 名称 | 含义 | 是否阻塞合并 |
|------|------|------|--------------|
| 🔴 Blocker | 阻塞 | 正确性/安全/数据丢失/合规，必须改 | 是 |
| 🟠 Major | 重要 | 设计缺陷、明显可维护性问题 | 是（自动打回） |
| 🟡 Minor | 建议 | 改进建议 | 否（记录为 follow-up） |
| ⚪ Nit | 吹毛 | 风格偏好（通常由预检覆盖） | 否 |
| 💬 Note | 说明 | 上下文/学习提示 | 否 |

- 每条评论（最终报告，非代码文件内容）结构：`{clause, severity, file, line, message, suggestion, confidence}`，其中 `clause` 引用《编码规范》的具体条款（如 `5.1` 函数短小、`6` 控制结构）。
- 置信度低于阈值的 🟠/🔴 标记为"待确认"，不直接阻塞，由作者显式确认或规范维护者复核。
- 风格类（Nit）若无预检覆盖才由评审子代理输出，避免与预检重复。

---

## 6. 评审执行标准（基于《编码规范》）

 评审子代理按以下维度逐项判定，每条结论对应《编码规范》的具体条款：

1. **正确性与边界**：空值、越界、并发、异常路径、资源释放。
2. **设计合理性**：是否符合《编码规范》中函数/模块/包设计；是否引入不必要复杂度（如圈复杂度超阈）。
3. **可读性与命名**：命名自解释、注释解释"为什么"、无死代码。
4. **测试充分性**：新增逻辑是否有对应测试，边界/异常分支覆盖，覆盖率未下降。
5. **安全与合规**：注入、越权、敏感信息、不安全依赖、license 风险。
6. **影响面**：是否破坏公开接口/行为，迁移与回滚是否安全。
7. **文档同步**：公共 API/配置项/行为变更是否更新文档。
8. **端到端行为**：关键用户路径在集成环境下是否按预期贯通；新增/修改的对外能力是否有 E2E 覆盖；E2E 失败是否可定位到具体服务与步骤。

> 预检子代理已覆盖的格式/Lint/类型/覆盖率问题，评审子代理**不再重复**输出，除非存在交叉判定（如命名影响可读性）。

## 7. 自动裁决逻辑（主 Agent）

```
if 任一🔴 未解决            -> 打回(附修订清单)
elif 任一🟠 置信度≥阈 且未豁免 -> 打回
elif 低置信🟠/🔴 待确认       -> 标记为待确认, 不阻塞但通知维护者
elif 全部🟡/⚪/💬            -> 允许合并
else                        -> 合并并规范化提交
```

- 作者以 `@agent-ignore: <规范条款> <理由>` 显式豁免时，需规范维护者事后复核；滥用将被记录并告警。
- 争议（如 Agent 反复打回同一问题）升级给规范维护者人工定夺，并回流《编码规范》防复发。

---

## 8. 合并方式（主 Agent）

- 优先 **squash merge** 为单一语义提交，或 **rebase merge** 保持线性历史。
- 提交信息由主 Agent 依据变更说明自动生成，含摘要与工单号。
- 禁止将 `WIP`、调试提交带入受保护分支（由门禁拦截）。

---

## 9. 与《编码规范》的衔接

- 《编码规范》是审查的**唯一标准来源**，不存在与之并列的独立规则集；Agent 的所有判定直接映射到规范条款。
- 审查中发现规范未覆盖或条款过时之处，由规范维护者更新《编码规范》，审查行为随之改变。
- 新成员/新 Agent 上线前，通读《编码规范》并以历史变更集做一次回放验证。
