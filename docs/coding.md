# 通用编码规范

> 适用范围：本规范为跨语言、跨项目的通用工程约定，覆盖**代码风格**与**项目结构**两个维度。
> 具体语言在遵循本规范的基础上，应结合其官方风格指南（PEP 8、Google Style Guide 等）落地。
> 目标：可读性、可维护性、可协作性。当规范与局部需求冲突时，以"清晰一致"为最高原则，并在评审中记录例外。

---

## 1. 通用原则

1. **可读优于聪明**：代码被阅读的次数远多于被编写的次数。优先选择直白、可预期的写法。
2. **一致性优先**：同一项目内必须保持一致；风格细节的选择不如"统一"本身重要。
3. **单一职责**：函数、类、模块、文件都应只做一件事，并把它做好。
4. **显式优于隐式**：意图、边界、依赖都应明确表达，避免"魔法行为"。
5. **最小惊讶**：行为与命名、约定相符，不引入反直觉的副作用。
6. **无用即删**：不保留被注释掉的代码、死分支、未使用的变量与导入。
7. **禁引用**：自述类文档严禁引用计划文档，禁止携带计划编号。
8. **git提交**：git提交信息必须为无人称自述口吻，禁止带计划编号。

---

## 2. 命名规范

命名是代码可读性最核心的部分。命名应**自解释**，避免使用需要额外注释才能理解的缩写。

### 2.1 通用约定

| 元素 | 推荐风格 | 示例 |
|------|----------|------|
| 变量 / 函数 | 小驼峰 `camelCase` 或蛇形 `snake_case`（按语言惯用） | `userCount` / `user_count` |
| 常量 | 全大写下划线 | `MAX_RETRY_COUNT` |
| 类 / 类型 | 大驼峰 `PascalCase` | `UserService` |
| 包 / 目录 | 小写连字符或下划线，不含空格 | `user-service` / `user_service` |
| 布尔值 | 以疑问词开头表达状态 | `isActive`、`hasPermission`、`canEdit` |

### 2.2 命名禁忌

- 禁止单字母命名（`i/j/k` 仅限循环索引，`x/y/z` 仅限坐标/数学上下文）。
- 禁止无意义前缀/后缀：`data`、`info`、`temp`、`obj`、`final`、`new`。
- 禁止中英混写命名：`getUserList` 而非 `get用户列表`。
- 禁止拼音与英文混用（`getYongHu` 应改为 `getUser`）。
- 集合名用复数（`users`），单元素用单数（`user`）；映射用 `实体→目标` 语义（`userIdToName`）。

### 2.3 作用域与长度

- 作用域越小，名称可越短；作用域越大，名称应越完整。
- 函数名应包含**动词**（动作）：`fetchUser`、`validateInput`、`renderChart`。
- 避免"动词+名词+副词"堆砌过长名称；过长往往意味着职责不单一。

## 3. 代码格式与排版

### 3.1 基础规则

- 统一使用 **UTF-8** 编码，文件末尾保留一个换行符。
- 统一缩进：团队约定 **2 或 4 个空格**（按语言惯用），**禁止使用 Tab 与空格混排**。
- 单行长度建议上限 **80–120 字符**（团队统一取值，如 100），超长需换行并保持对齐。
- 每行一个语句，禁止用 `;` 拼接多条语句。

### 3.2 空白与空行

- 二元运算符两侧各一个空格：`a = b + c`。
- 逗号/冒号后一个空格，前无空格：`func(a, b)`。
- 用空行分隔逻辑段落，但**不要超过 2 个连续空行**。
- 函数、类、文件块之间用空行分隔，提升视觉边界。

### 3.3 括号与对齐

- 括号、方括号、花括号内不紧贴内容：`arr[0]`、`func(x)`、`{ key: value }`。
- 换行后的参数/链式调用应与首参数对齐，或统一增加一个缩进层级。

### 3.4 自动化

- 使用格式化工具统一风格：**Prettier**（JS/TS/JSON/MD）、**Black/ruff**（Python）、**gofmt**（Go）、**clang-format**（C/C++）。
- 提交前自动格式化；CI 中加入格式化检查，**禁止人工手动对齐**。

## 4. 注释与文档

### 4.1 原则

- 注释解释 **"为什么"**，而不是 **"是什么"**；代码本身应说明"是什么"。
- 好的命名可以替代大部分注释；不要为显而易见的代码写注释。
- 注释与代码同步更新，过时注释比无注释更危险。

### 4.2 注释类型（禁止带计划编号）

- **行内注释**：仅当逻辑不直观时使用，与代码间隔至少 2 个空格。
- **块注释**：解释复杂算法、业务规则、边界条件。
- **更新**：功能代码更新注释不解释为什么取消放弃原**功能，只解释当前代码

### 4.3 文档注释（禁止带计划编号）

- 公共 API、类、导出的函数必须有文档注释（JSDoc / docstring）。
- 文档应包含：功能概述、参数（类型与含义）、返回值、抛出的异常、使用示例（复杂时）。
- **更新**：功能代码更新注释不解释为什么取消放弃原**功能，只解释当前代码

### 4.4 注释禁忌

- 禁止保留被注释掉的代码（用版本控制而非注释管理历史）。
- 禁止"讲故事"式、情绪化、与代码无关的注释。

## 5. 函数与模块设计

### 5.1 函数

- **保持短小**：单个函数建议 ≤ 50 行；超过时应考虑拆分。
- **单一职责**：一个函数只做一件事；多职责应拆分为多个协作函数。
- **参数 ≤ 3–4 个**；超过时封装为对象/结构体（尤其布尔开关参数应改为选项对象）。
- **无副作用**：纯函数优先；若产生副作用（IO、状态变更）需在命名或文档中显式说明。
- **单一出口非强制**，但深层嵌套应用"卫语句（early return）"扁平化：
  ```text
  if (!input) return;
  if (!valid(input)) return;
  // 主逻辑
  ```
- 避免 `null`/空值作为"正常值"返回，优先使用空集合、Optional/Maybe 或明确异常。

### 5.2 模块 / 文件

- **一个文件一个主题**：按"职责"而非"类型"组织文件（如 `userService` 而非 `utils`）。
- 文件长度建议 ≤ 400–500 行，过长应拆分。
- 文件顶部放置：许可证（若需）、模块说明、导入（按语言/分组排序）。
- 导入顺序：标准库 → 第三方库 → 内部模块，各组之间空行分隔。
- 避免循环依赖；依赖方向应单一、可分层。

### 5.3 类与类型

- 优先组合而非继承；继承仅用于"is-a"关系。
- 公开 API 最小化，隐藏内部实现细节（封装）。
- 构造函数不应执行重逻辑或 IO；复杂初始化通过工厂或显式 `init` 方法完成。
- 不可变优先：能用 `const`/只读字段的就不要用可变状态。

## 6. 控制结构与错误处理

- 避免过深嵌套（≤ 3 层）；用卫语句、提取函数、策略表降层。
- 禁止"吞掉"异常：空 `catch` 必须至少记录日志或注释说明原因。
- 错误信息应可操作：说明"什么 failed、为什么、如何修复"，而非仅 `Error occurred`。
- 区分"可恢复"与"不可恢复"错误；业务校验错误不应使用异常机制承载正常流程。
- 资源（文件、连接、锁）必须成对释放，使用语言提供的 `try/finally`、`with`、`RAII` 等机制。

---

## 7. 项目结构

### 7.1 命名与文件

- 文件/目录名使用其所属语言的惯用风格，且全项目统一。
- 测试文件与被测文件同名 + 后缀（`userService.test.ts`、`test_user_service.py`）。
- 每个模块提供明确的入口与导出清单（避免"桶文件"无脑 re-export 导致混乱）。
- 测试文件待每个子目录的test目录（没有就新建，不要全待该功能、机制的根目录）。例：example\test\ and example\example-example\test\

### 7.2 配置管理

- 密钥、环境相关值通过环境变量或密钥管理工具注入，**禁止硬编码**入仓库。
- 配置文件应可读、可校验，提供 `.example` 模板（如 `.env.example`）。
- 区分"构建期配置"与"运行期配置"，避免混淆。

### 7.3 依赖与工具链

- 使用依赖锁文件（lockfile）保证可复现构建。
- 定期更新依赖并审查安全告警；禁止引入无维护、无许可证的包。
- 统一代码格式化、Lint、类型检查、测试在 CI 中执行。

---

## 8. 落地与执行

1. **文档化**：本规范放入仓库 `docs/`，并在 `README` 中链接。
2. **工具化**：配置格式化、Lint、类型检查，提交前自动运行（pre-commit）。
3. **CI 守门**：PR 必须通过格式检查、Lint、测试、类型检查方可合并。
4. **评审常态化**：Code Review 以本规范为基准，分歧在团队内讨论后回填文档。
5. **定期修订**：每季度回顾一次，随技术栈演进更新。
