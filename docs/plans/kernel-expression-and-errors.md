# 内核表达力与错误定位：实施计划

> **状态：已完成**（worktree，未合并）。失败节点定位 `at`/`def`/`callAt` 全程透传；`pred`/`get` 已加；算术/构造另立项落地为 `arith`/`list`/`obj`/`getOr`（原语 14）。内核 255 用例全绿。

> 口径来源：`docs/kernel.md`（内核设计，唯一权威）。
> 本文件属 `docs/plans/`，只写「怎么做」；冲突以设计文档为准。
> 来源：工具链多轮第三方作者实测暴露的两个内核侧缺口。

## 项目一：运行期失败节点定位

### 现状
`machine.ts` 出错抛 `KernelError(code)`，`evaluation` 收成 `{ ok:false, error }`；**不带失败节点**，工具链无法把运行期错误映射回源行。这是作者反馈里最大的调试痛点。

### 设计（加法式、向后兼容）
- `KernelError` 增可选 `at`：从入口 term 起、沿实际求值路径的索引/键序列（如 `[1,2,0]`）。
- `evaluation` 返回 `{ ok:false, error, at? }`；`run`/observations 可选携带，调用方不受影响。
- 跨 def 规则：进入 `call`/`fold` 被调 term 后失败时，`at` 指向**调用点**，另设 `def` 字段标出被调 term 哈希（或采用「路径分段」形状），使工具链能把「调用点 + 被调 term 内路径」拼回源。
- 覆盖所有失败路径：`bad_term`/`bad_var`/`missing_path`/`bad_fun`/`missing_ref`/`gas`/`depth`/`bad_cond`/`not_a_list`/`eff_error`。
- 不改链格式、不改 `entryHash`/`argsHash`、不改既有错误码语义；老日志照常重放。

### 验收
- 内核既有 244 用例全绿；宿主全套无回归。
- 嵌套失败节点的 `at` 正确；`call`/`fold` 跨 def 语义明确并有测试。
- 工具链据 `at` 能把错误映射回糖化源指针（依赖工具链项目）。

## 项目二：算术与数据构造原语

### 现状
10 原语无算术、不能构造新数据；判定只能「选择 / 投影」，不能「推导新值」。作者实测：求和、加权、tie-break、构造返回对象、给候选补字段都写不出。

### 设计决策（最小加法集）
- **算术**：新增 `["arith", op, a, b]`，`op ∈ add/sub/mul`；仅接受有限数（`t()` 已保证有限），结果非有限抛 `bad_arith`。**先不加 `div`**（除零/非终止小数语义复杂，收益低）。
- **构造**：新增 `["list", [term...]]`（新列表）与 `["obj", { k: term... }]`（新对象）；键序由 `canonicalJson` 统一，`cmp`/哈希口径不变。
- **不加**：`cons`/`append`（`list` 已够）、动态字段名（`get` 保持静态路径）、lambda/递归/while（内核设计拒绝）。
- 全部为**加法式**：不改既有原语语义，老日志照常重放；新日志在旧实现报 `bad_term` 而非算错。
- 终止性不受影响（算术/构造皆结构性终止）。

### 边界影响
- 「term = 选择与编排，数值归执行件」这条边界**外移一格**：纯数值聚合与结果组装可进 term；重计算仍归执行件。
- 原语数 10 → 13（`arith`/`list`/`obj`）；`kernel.md` §十三、`README.md` 原语清单同步。

### 验收
- 内核用例全绿 + 宿主无回归；`cmp` 全序、`canonicalJson`、哈希在含新原语的世界里稳定。
- 工具链加对应糖（`t.add`/`t.obj`/`t.list`）与降级规则，第三方作者复测「按 score 求和 / 构造返回对象」可行。

## 顺序

1. 项目一（错误定位）先做：风险低、直接解作者最大痛点。
2. 项目二（算术/构造）后做：改动面大，按「最小加法集」一次到位并同步文档。
3. 两者完成后，工具链据 `at` 做源映射、据新原语扩糖，再跑第三方作者复测。
